# Engine-dev analysis: 2026-09-25T124209_sf1600_win

Result: win by checkmate, 55 plies, 0 mistakes >=100cp for us. Nothing to blame here tactically.

## Mate conversion speed (once available)
Black's decisive blunder is ply 50 (`e4`, best was `Qe8`): eval flips from -944 to a
found mate (-9997). From that point our engine needed exactly 3 more moves —
`Qxh4+` (51), `Qe5+` (53), `Qhe7#` (55) — and every one of them matches Stockfish's own
top choice (drop_cp ~0). So once mate was on the board, conversion was optimal: no
wasted tempo, no horizon wobble. This is not a problem to fix.

The only pre-mate softness is ply 49 (`Qg4` vs best `Qxg8+`, drop_cp -90 i.e. actually
fine/improving) — engine declined a free queen-with-check in favor of a different won
line. Not a mistake by the eval, but it shows the root loop (`best_move` in
`engine/src/main.rs`) has no aspiration window and re-searches every root move from
`alpha = -INF` at every iterative-deepening depth; only the single previous best move is
reordered to the front (`moves.retain`/`insert(0, ...)`, lines ~184-185). With many
roughly-equal winning replies in a won position, the search has weak incentive to find
the single fastest mate rather than "a" won move — separate from, and complementary to,
the queued PVS+LMR/TT work.

## Fragility at 5 s/move
1. **`think_time` (main.rs:218-233) mishandles low-clock + increment.** When `movetime`
   isn't given, `ms = wtime/30 + winc`, uncapped by remaining `wtime` itself (only capped
   at the hard 5000 ms ceiling). E.g. `wtime=200, winc=4000` → engine thinks for ~3.9 s
   with 0.2 s left on the clock → clock loss / UCI-illegal move under any time-control
   other than a flat `movetime`. Currently dead code (the arena always sends `go
   movetime`, confirmed in `arena/play.py`'s `chess.engine.Limit(time=...)`), so it
   hasn't bitten us yet, but it's a live landmine if campaign/arena tooling ever switches
   to `wtime/btime` (e.g. a future blitz-style gauntlet).
2. **Time-check granularity assumes cheap nodes** (`self.nodes & 2047 == 0` in both
   `negamax` and `quiesce`, main.rs:82 and :121). Fine today, but as `evaluate()` grows
   (king safety, pawn structure — already queued) each node gets pricier; 2048-node
   polling could overshoot the 5 s deadline in a single check interval. Worth switching
   to a node-count that adapts, or checking every N nodes *and* a wall-clock fallback
   inside the move loop, before adding heavier eval terms.

## Ranked suggestions (new items only, not already queued)
1. **Cap `think_time` by remaining clock, not just the 5 s ceiling** — `ms =
   min(wtime.saturating_sub(margin), wtime/30 + winc, 5000)` in `think_time`
   (main.rs:218). ~15 min fix. Elo impact ~0 today (movetime-only arena) but prevents a
   guaranteed loss-on-time the moment any wtime/btime-based match is run; test with a
   unit test feeding `wtime=200 winc=4000` and asserting `duration <= wtime`.
2. **Aspiration windows around the previous iteration's score** in `best_move`
   (main.rs:160-190): start each depth with `alpha = prev_score - 50, beta = prev_score +
   50`, widen on fail-high/low. ~1-2 hr with TT still absent (works even without a hash
   move). Expect faster deepening in won/lost positions → finds mate-in-N a ply or two
   sooner and frees clock for other moves. Est. +10-20 Elo. Test: self-play gauntlet vs
   current build (`arena.gauntlet`), plus node-count comparison on this game's ply
   41-49 subtree (should reach greater depth in the same 5 s).
3. **Re-check the deadline right after `evaluate()` calls inside `quiesce`**, not only
   every 2048 nodes, once eval gets heavier — cheap insurance (~10 min) against future
   5 s overshoot; no Elo gain by itself, just a correctness/robustness guard to add
   *before* landing the queued king-safety/pawn-structure eval work.

No change to the existing improvement-queue ordering is warranted by this game — the
mate was found and delivered cleanly; the queue's TT/PVS/killer items remain the biggest
expected wins and should stay first.
