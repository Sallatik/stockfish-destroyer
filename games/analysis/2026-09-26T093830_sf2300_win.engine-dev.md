## TT correctness review (tt.rs + its use in `negamax`) — no correctness bugs found
- Mate scoring: `to_tt`/`from_tt` add/subtract `ply` exactly like Stockfish's `value_to_tt`/`value_from_tt` (root-relative <-> node-relative), verified by hand against both unit tests; sign symmetric for the losing side too.
- Bound handling at cutoffs (Exact/Lower/Upper vs alpha/beta, `main.rs:113-120`) is textbook and correct. The `ply > 0` guard is inert rather than wrong: `negamax` is never invoked at ply 0 (root always calls it on children at ply 1), so the guard never actually fires either way.
- All three `self.stopped` early-returns happen before `tt.store` (entry, mid-loop-after-child, and the implicit skip when moves are empty), so a mid-search timeout can never write a partial/corrupt entry — verified by tracing every return path.
- Repetition/50-move draws return before the TT probe/store, so draw scores are never cached directly. The one residual theoretical impurity — a parent's cached score can implicitly depend on a repetition that is path-specific, not position-specific — is the same accepted limitation every TT+repetition-detection engine has; not worth spending time on.
- Hash collisions: full 64-bit Zobrist key is stored and re-verified on every probe, so a slot collision can never return a wrong-position's score.

## Ply-35 Bc4+ vs Qxc8: horizon effect, not ordering
Root ordering can't be the cause by construction: `best_move` (`main.rs:199-230`) scores every legal root move to the same depth every iteration and keeps the running argmax, so Qxc8 always got a complete, fair, full-depth search — whichever move the loop returns is the search's genuine best per its own (limited) evaluation, independent of list order (this is the same full-window property the task already cleared). Internal-node MVV-LVA/hash-move ordering (`main.rs:122-123`) is also correct, it just decides *how much* of the tree gets explored below the root. Replaying the exact position into `bin/destroyer-engine-v5` confirms the mechanism: it reaches depth 9 (~9.5M nodes) in 5s with the score still moving — 943 flat through depth 4, then 1101, 958, 987, 947, 983 at depths 5-9 — a sign the line isn't settled. At that horizon the engine finds the real Bxd5+/Rg1+/Qxe5 queen grab (which paid off only because SF2300 misdefended with d5/Kg6/Ng4 instead of its own suggested Be6/Kh5), but 9 plies isn't enough to also fully credit Black's best defense 18...Be6, which caps Bc4+ at +547 vs Qxc8's clean +769. With no killer/history heuristic yet, a quiet only-defense move like Be6 gets no ordering help at the nodes below the root, which is the indirect way move ordering *does* contribute — by capping effective depth, not by hiding Qxc8 at the root. This is exactly the class of mistake "killer/history" and "check extensions" already in the queue are meant to fix; good regression evidence for both, doesn't change their order.

## Ranked code-level items (max 3)
1. **Tighten TT replacement policy + grow the table** — `tt.rs::Table::store`: `bound == Bound::Exact` unconditionally replaces regardless of depth, so a depth-2 exact entry can evict a depth-8 bound. At depth 9 the search already pushes ~9.5M nodes through only 2M slots (`Table::new(21)` in `main.rs`), so this thrashes hard. Change the guard to `depth as u8 + 2 >= e.depth` before letting Exact override, and bump to `Table::new(23)` (~8M entries, ~256MB, cheap on the M5 Pro). Rough est. **+5-15 Elo**. Test: `arena.gauntlet` of current build vs this change only; secondary check: node count to reach a fixed depth on a stored tactical FEN should drop.
2. **Probe/store the TT inside `quiesce`** — `main.rs::Search::quiesce` never touches `self.tt`, so forcing/capture-heavy lines like the ply-35 king hunt re-derive identical qsearch subtrees every time they transpose. Add a probe at entry (cutoff + seed alpha/stand-pat) and a store before each return, gated on `!self.stopped` exactly like `negamax`. Rough est. **+10-20 Elo**, likely more in sharp tactical games like this one. Test: same gauntlet, plus a unit test asserting lower qsearch node counts on a FEN with a repeatable capture sequence.

## Risks
- `Table::new(23)` is ~4x today's ~64MB per engine process; confirm headroom before shipping under 4-8 concurrent campaign/gauntlet slots — a memory or cache-thrash problem on the shared machine, not the 5s/move budget itself.
- Any TT write added to `quiesce` must gate on `!self.stopped` exactly like `negamax`'s store, or it reintroduces the corrupted-entry class of bug this file currently avoids.
- Aside, not a game risk: `think_time` (`main.rs`) ignores a bare `go depth N` and always defaults to ~5s — harmless for real games (arena always sends `movetime`/`wtime`) but will silently mislead any future fixed-depth analysis/bench tooling; a 10-minute fix if that tooling gets built.
- Neither ranked item touches `go`/time parsing or `bestmove` output, so the 5s/move rule and UCI correctness are unaffected.
