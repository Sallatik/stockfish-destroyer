## 2. Diagnosis — root causes that cost the most

1. **Search depth ceiling.** No TT, no killers/history, no PVS/LMR means every iterative-deepening pass re-explores from scratch with only MVV-LVA + "last best move to front" ordering. Effective branching factor stays high, so ~depth 7-9 is the ceiling in 5s (consistent with the documented depth-7 @1s baseline). An 11-ply forced sequence with several forced non-capture replies is simply out of reach for full-width search — quiescence can't help because most of the line isn't a chain of captures.
2. **Total absence of king safety in `evaluate()` (`engine/src/main.rs:34-42`).** Three of the six flagged mistakes (ply 41, 43, 45 — the ones that actually lost the game) are king-safety blunders: opening lines to our own king (gxh5), ignoring a mating attack in favor of a random pawn push (a5), and playing a move that doesn't address king exposure at all (Nd2). Material-only eval literally cannot see any of this, at any depth.
3. **Root move-selection bug** (see #4 below) makes move ordering/best-move choice at the root less reliable than it should be, likely contributing to the smaller ply-19/21/27 losses.

## 3. Confirms / changes queued priority
- **Confirms #4 (TT) + #5 (killers/history) + #7 (PVS/LMR) as top priority** — this game is a clean example of a loss caused directly by insufficient depth on a forcing line, exactly what those items target.
- **Raises #8 (king safety) priority sharply.** It should not wait behind #2 (repetition) or #3 (opening book) — those cost nothing in this game, king safety cost the whole game. Recommend pulling a *minimal* king-safety term (pawn-shield / open-file-near-king penalty) into the same commit as #1 (PeSTO PSTs), since PSTs alone only partially discourage this via king-square tables.

## 4. New, ranked action items (not already queued)

1. **Fix root search-window bug in `Search::best_move`** (`engine/src/main.rs:126-152`). The loop calls `-self.negamax(&child, depth-1, -INF, -alpha, 1)` for *every* move, so after the first move, later moves are searched with `beta = -alpha` (a null window). If a later move's true score exceeds alpha, the child search fails high and returns exactly the window bound, which negates back to `score == alpha` at the root — failing the `score > alpha` check and silently discarding a possibly-better move. Fix: on `score > alpha` from a null-window probe beyond the first move, re-search that move with the full `(-INF, -alpha)` window (standard PVS re-search) before accepting/rejecting. Effort: ~30-60 min. Expect **+10-20 Elo**. Test: A/B gauntlet (`arena.gauntlet`) old vs fixed build, 50+ games.
2. **Add check extensions in `negamax`** (`engine/src/main.rs:51`): `let ext = if pos.is_check() && depth < CAP { 1 } else { 0 }; ... depth - 1 + ext`. This directly targets forcing lines like the one that lost this game (`...Nxd3+`, `...Qh1+`) without ballooning branching factor everywhere (only applies when in check). Cap total extensions per line (e.g. via a ply-indexed counter) to bound worst case. Effort: ~1h. Expect **+20-40 Elo**, best realized once combined with TT (queued #4) so extended lines don't blow the time budget. Test: gauntlet vs previous build; watch average depth-per-move doesn't collapse in tactical middlegames.
3. **Quiescence capture pruning** (`engine/src/main.rs:82-121`): skip captures with a clearly negative MVV-LVA-style SEE approximation (e.g. `victim_value - attacker_value < -100` and not in check/not a check-evader) before recursing. Cuts wasted quiescence nodes in piece-heavy middlegames, freeing time for the main search to reach an extra ply. Effort: ~1h. Expect **+10-20 Elo**. Test: measure nodes/sec and depth-reached at move ~20-25 of this exact game (FEN at ply 41/43) before/after; gauntlet.
4. **Mate-distance awareness**: report `score mate N` in the `info` line (currently always prints raw `cp`, so mate scores show as absurd cp values like 9994) and add simple mate-distance pruning (`beta = beta.min(MATE - ply)`) at the top of `negamax`. Mostly a correctness/diagnostics fix, with a small speed bonus once actual mates are found nearby. Effort: ~30 min. Expect **+5-10 Elo**. Test: unit-test on a known KQvK mate FEN; confirm `info` output.

## 5. Risks
- The `go` command handler runs `best_move` synchronously on the stdin-reading thread; there is **no `stop` command handling at all**. If a harness ever sends `stop` mid-search, it will queue unread until our own `deadline` naturally elapses and `bestmove` is emitted — internal deadline still caps us at <5s, so the hard rule isn't violated, but the engine will never respond faster than its own budget even if asked to. Not urgent, but note before adding pondering/multi-threaded search.
- Check extensions (#2) and any future recapture/singular extensions must stay bounded (ply cap) — the existing node-count deadline check (`nodes & 2047 == 0`) is time-safe regardless, but an unbounded extension could waste the whole 5s budget on one bad line and starve other root moves of any search at low iterative-deepening depths.
- No node/depth logging is persisted per game (arena discards `info` lines), so "depth reached in 5s" here is inferred from the documented depth-7 @1s baseline, not measured directly for this game. Worth having the arena capture the last `info depth` line per move into the JSON for tighter future diagnosis — cheap, no Elo effect, but improves the next analysis loop.
