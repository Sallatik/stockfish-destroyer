## Diagnosis — Rad1 focus
Directly tested `bin/destroyer-engine-v4` on the ply-29 FEN at 5s/move: reaches **depth 6** (4.6M nodes), picks Rad1, cp153. Re-tested on the **current `bin/destroyer-engine-v5`** (TT + hash-move already merged): still depth 6, still picks Rad1, cp153 — TT halves the node count (2.25M) but adds **zero** extra depth on this position. Stockfish's point: Bf4 first, so that after a forced ...Nxf3+ Qxf3 Bxf3 the bishop already on f4 has **Bxc7** regaining the queen — a resource ~5 plies deep that a fixed 6-ply full-width search with no pruning/extensions can only just barely reach, and doesn't.
PST check (`engine/src/eval.rs`, phase 22/24 at this FEN): rook a1→d1 MG -19→+17 (**+36 MG, +33.7 tapered**); bishop e3→f4 MG +14→+12 (**-2 MG, -2.1 tapered**). Net **+35.75 cp bias toward Rad1 from the table alone** — real and reproducible, but only ~27% of the 133 cp error, and it encodes a generally-correct rule (get the rook off the back rank). **Verdict: horizon/depth, not a table bug.** Do not retune d1/e1.
